### 6.5 迁移必读坑点矩阵

下面这些坑，都是这次真实踩过、并且已经通过源码和隔离开发验证过的。新 AI 如果不先读这一节，最容易重复犯错。

#### 坑 1. 只跑 `npm run build:dev`，结果界面还是旧的

- 现象：
  - 你明明已经把源码里的默认布局改回来了，但启动后还是旧界面
  - 最典型就是明明删了 `Goose / DeerFlow` 默认入口，结果窗口还是先出来这套
- 真实根因：
  - `npm run build:dev` 只会重打 Electron / Vite 前端
  - 它不会重打 Go 后端 `wavesrv`
  - 而 starter layout 是在 `pkg/wcore/layout.go` 里，由 `dist/bin/wavesrv.*` 实际执行
- 正确做法：
  1. 只要改了 `pkg/**`、`cmd/**`、`schema/**`、启动 bootstrap、starter layout、后端连接逻辑，就不要只跑前端构建
  2. 必须额外执行 `npm run build:backend:windows`
  3. 然后再 fresh 重启隔离开发实例验证
- 关键文件：
  - `pkg/wcore/layout.go`
  - `scripts/build-backend-windows.ps1`
  - `scripts/wave-windows-common.ps1`

#### 坑 2. 把 `dev:linked` 写成“每次都 fresh”，会极大放大白屏概率

- 现象：
  - 开发版总是很难起来
  - 窗口壳起了，但长时间没内容
  - `5300` 明明监听了，`/`、`/@vite/client`、`/frontend/app/app.tsx` 这种基础请求却能卡到 `30s`
- 真实根因：
  - 旧版 `scripts/dev-instance.ps1` 每次 `npm run dev:linked` 都会删：
    - `.tmp/dev-linked/current/data`
    - `.tmp/dev-linked/current/electron-userdata`
  - 这会把每次启动都变成“首启 + 冷缓存”
  - 再叠加当前首屏依赖重，白屏概率会被放大
- 正确做法：
  1. `dev:linked` 默认应当是“持久化隔离实例”
  2. 只有在你明确要验证“首启 / 冷状态 / 新布局初始化”时，才使用 `-FreshState`
  3. 不要把“每次都 fresh”当作日常开发默认值迁到新仓库
- 关键文件：
  - `scripts/dev-instance.ps1`
  - `.tmp/dev-linked/current/data`
  - `.tmp/dev-linked/current/electron-userdata`

#### 坑 3. `frontend/wave.ts` 顶层依赖太重，会导致“窗口出来了，但内容迟迟不来”

- 现象：
  - Electron 窗口不是没起来，而是只有一个空壳
  - 看起来像“启动了但没内容”
  - 很容易误以为是 Electron、Vite 或浏览器层问题
- 真实根因：
  - `frontend/wave.ts` 顶层如果同步 import `App` / `BuilderApp` / Monaco 相关依赖，首屏渲染会被整个拖住
  - 如果再把 `setWindowInitStatus("ready")` 放在 `document.fonts.ready` 之后，就会让“ready 信号”也跟着字体请求一起变慢
- 正确做法：
  1. `initBare()` 必须尽量轻
  2. `setWindowInitStatus("ready")` 要尽早发，不要继续被字体加载阻塞
  3. `App` / `BuilderApp` 用动态导入，不要回退成顶层静态导入
  4. 首屏日志点至少保留：
     - `Init Bare`
     - `Init Wave importing App`
     - `Init Wave imported App`
     - `Wave First Render Done`
- 关键文件：
  - `frontend/wave.ts`

#### 坑 4. 首屏 modal 链会把 `builder / onboarding / monaco` 提前拖进来

- 现象：
  - 窗口看起来卡在空白期
  - `dev.log` 里已经能看到基础页面回了，但后面会长时间 pending：
    - `frontend/builder/**`
    - `frontend/app/onboarding/**`
    - `monaco-editor/**`
- 真实根因：
  - `ModalsRenderer -> modalregistry -> builder/onboarding/monaco` 是一条重链
  - 如果 modal registry 首屏静态导入，就会把这些本来不该在首屏出现的重量依赖一起拉进来
- 正确做法：
  1. `modalregistry.tsx` 保持 `lazy()`
  2. `modalsrenderer.tsx` 保持 `Suspense`
  3. 不要在迁移时为了“看起来简单”把它们再改回同步 import
- 关键文件：
  - `frontend/app/modals/modalregistry.tsx`
  - `frontend/app/modals/modalsrenderer.tsx`

#### 坑 5. `Goose / DeerFlow / promptoptimizer` 默认入口线是污染，不是当前产品语义

- 现象：
  - 一 fresh 启动就进入错误的工作台
  - 即使前端看起来改对了，最后窗口还是跑偏
- 真实根因：
  - 默认入口污染不是单点，而是双点：
    1. `frontend/wave.ts` 的 embedded projects 启动分叉
    2. `pkg/wcore/layout.go` 直接改写 starter layout
- 正确做法：
  1. 迁移新版时把这条线明确标成“不要迁”
  2. 如果未来还想保留 Goose 相关 view，只能作为可选独立 view 保留
  3. 不允许再挂到默认启动链
- 关键文件：
  - `frontend/wave.ts`
  - `pkg/wcore/layout.go`

#### 坑 6. fallback atom 可以防 crash，但也会把真正的初始化问题伪装成“加载中...”

- 现象：
  - 不再直接报错或白屏
  - 但界面可能一直停在“加载中...”
  - 很容易让人误判成“只是再等等就好”
- 真实根因：
  - 类似 `atoms?.staticTabId ?? fallbackAtom`、`atoms?.workspace ?? fallbackAtom` 的写法，会把原本应该暴露出来的状态缺失吞掉
  - 它能防止初始化窗口期直接 crash，但也会掩盖真正的 workspace hydration 问题
- 正确做法：
  1. 这类 fallback 只能当“防白屏护栏”，不能当成正式状态来源
  2. 迁移时如果保留这层护栏，必须同时保留首屏日志和 workspace hydration 验证
  3. 不能因为“不报错了”就判断功能没问题
- 关键文件：
  - `frontend/app/workspace/workspace.tsx`
  - `frontend/app/workspace/widgets.tsx`
  - `frontend/app/workspace/favorites.tsx`
  - `frontend/app/workspace/servers-panel.tsx`
  - `frontend/app/workspace/path-history-panel.tsx`

### 6.8 开发版测试、隔离启动与打包规程

这一节是给新的 AI 用的“操作规程”，不是建议语气。照着做，才能避免顶掉正式版，或者打出来的安装包和源码不一致。

#### 6.8.1 开发版必须怎么启动

开发版不要直接跑裸的 `npm run dev`，当前仓库规则要求优先使用隔离实例：

1. 启动隔离开发版：
   - `npm run dev:linked`
2. 查看当前隔离实例状态：
   - `npm run dev:linked:status`
3. 停止隔离实例：
   - `npm run dev:linked:stop`
4. 如果你需要验证“首启 / 冷状态 / starter layout / 初始化迁移”：
   - `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/dev-instance.ps1 -Action start -FreshState`

#### 6.8.2 为什么这套开发版不会顶掉正式版

原因不是“运气好”，而是脚本本身就做了隔离：

1. `scripts/dev-instance.ps1` 会把开发版状态写到：
   - `.tmp/dev-linked/current/config`
   - `.tmp/dev-linked/current/data`
   - `.tmp/dev-linked/current/electron-userdata`
2. 启动时会显式设置：
   - `WAVETERM_CONFIG_HOME`
   - `WAVETERM_DATA_HOME`
   - `WAVETERM_ELECTRON_USER_DATA_HOME`
3. 运行主体是仓库里的：
   - `node_modules/electron/dist/electron.exe .`
4. 也就是说，隔离开发版和正式安装版不是共用同一套用户数据目录

结论：

- 正确使用 `dev:linked` / `dev:linked:stop` / `dev:linked:status` 时，开发版不应顶掉正式版
- 真正危险的是：
  - 乱开多个开发实例
  - 不走隔离脚本，直接自己手搓一套启动方式
  - 不停旧实例就继续拉新实例

#### 6.8.3 开发版验证时必须注意什么

1. 一次只保留一个隔离开发实例
2. 先 `status` 再判断，不要靠肉眼猜哪个窗口是谁
3. 改了前端后至少跑：
   - `npm run build:dev`
4. 改了 Go 后端 / starter layout / schema / backend 启动链后，必须再跑：
   - `npm run build:backend:windows`
5. 最终必须看真实窗口，而不是只看日志
6. 如果你要证明“没有顶掉正式版”，应以隔离目录和进程来源为证据，而不是口头判断

#### 6.8.4 安装包应该怎么打

当前仓库已有现成脚本，优先顺序如下：

1. 标准 Windows 打包入口：
   - `npm run release:win`
2. 如果当前工作树允许 dirty 打包：
   - `npm run release:win:allow-dirty`

这条脚本内部会做：

1. `npm run build:prod`
2. `npm run package:win` 或 `npm run package:win:allow-dirty`
3. 从：
   - `make/<version>/WAVE-win32-x64-<version>.exe`
   拷贝一份到桌面目录

#### 6.8.5 安装包为什么要优先走 `release:win`

因为它不只是“打包”，还顺手做了结果投递：

1. 默认桌面目录参数是：
   - `D:\DeSK`
2. 产物会被复制成：
   - `D:\DeSK\WAVE-win32-x64-<version>-fix-<sha>.exe`
3. 还会打印这个拷贝后文件的 `sha256`

所以如果你的要求是“打包完要在 D 盘 desk 放一份”，当前仓库已经支持，不需要新 AI 再自己发明一套复制逻辑。

#### 6.8.6 打包前必须注意的坑

1. 只打前端、不打 Go 后端，就可能把旧的 `wavesrv` 一起装进安装包
2. `electron-builder.config.cjs` 已经做了两层保护：
   - 检查 `dist/main` / `dist/preload` / `dist/frontend` 是否存在
   - 检查 `dist/bin/wavesrv.*` 是否存在且不陈旧
3. 但新的 AI 仍然不能偷懒，正确顺序应该是：
   1. 前端改动：
      - `npm run build:prod`
   2. 只要动了 Go / backend / schema：
      - `npm run build:backend:windows`
   3. 再执行：
      - `npm run release:win`
4. 如果工作树是 dirty，默认 `release:win` 会拒绝继续；只有你明确接受 dirty 打包时，才使用：
   - `npm run release:win:allow-dirty`

#### 6.8.7 新 AI 打包后的最低确认项

1. 安装包主产物存在于：
   - `make/<version>/WAVE-win32-x64-<version>.exe`
2. 桌面副本存在于：
   - `D:\DeSK\WAVE-win32-x64-<version>-fix-<sha>.exe`
3. 控制台打印出最终 `sha256`
4. 若这次打包包含 Go 侧改动，必须确认不是旧后端残留
5. 若这次打包用于用户测试，仍建议先用隔离开发版跑一遍关键路径，再给安装包
