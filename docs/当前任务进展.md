# 当前任务进展

## 唯一目标
- 把 `Wave` 里的新内嵌浏览器 `Beta Browser` 当成一个正常浏览器容器来用。
- 用这个 `Beta Browser` 打开一套干净的 `OpenVSCode Server`。
- 在这套干净的 `OpenVSCode Server` 里，只验证 `Codex` 能不能真正运行。

## 当前关系锁定
- `Wave` 是宿主。
- 浏览器在 `Wave` 里面，就是 `Beta Browser`。
- `OpenVSCode Server` 是被这个内嵌浏览器打开的页面。
- 当前不是继续沿用旧实验环境，而是从干净状态重来。

## 这件事到底不是在做什么
- 不是重写浏览器内核。
- 不是改正式版 `Wave`。
- 不是继续在旧的脏 `OpenVSCode` 副本上乱试。
- 不是走源码编译、`npm install`、`electron` 下载那条线。
- 不是先讨论一大堆概念，再没有结果。

## 我们现在已经对齐的事实
- `Beta Browser` 本质上是 `Wave` 里的 Electron `webview` 内嵌浏览器容器。
- 它已经能正常打开网页，也已经能正常承载 `OpenVSCode Server` 页面。
- 之前扩展卡死时，同一个 `OpenVSCode` 实例在 `Beta Browser` 和普通浏览器里都一样卡死。
- 所以当前没有证据表明是 `Beta Browser` 天生不能跑这些扩展。
- 更大的嫌疑是之前那套 `OpenVSCode` 被改脏了，或者那套实例本身就不干净。

## 现在真正要交付的结果
- 在 `Wave` 开发版里点开 `Beta Browser`。
- `Beta Browser` 打开一套干净的 `OpenVSCode Server`。
- 在 `OpenVSCode` 里能看到并安装/识别 `Codex`。
- 点开 `Codex` 以后，不再一直停在加载状态。
- 至少要有一个明确正向证据：
  - `Codex` 侧栏真正打开
  - 或 `Codex` 真正激活并可交互

## 什么才算完成
- 不是“页面能打开”就算完成。
- 不是“扩展图标出现了”就算完成。
- 不是“按钮能点”就算完成。
- 只有 `Codex` 真正激活、真正打开、真正能用，才算完成。

## 当前唯一允许的路线
- 主战场只认 `Wave` 开发版里的 `Beta Browser`。
- 只使用官方预编译的干净 `OpenVSCode Server`。
- 只安装并验证 `Codex`。
- 普通浏览器如果使用，只能做最小对照，不能替代 `Wave` 里的验证。
- 如果普通浏览器正常、`Beta Browser` 不正常，再回头查 `Wave` 内嵌层。
- 如果普通浏览器也不正常，就继续查这套干净 `OpenVSCode` 实例本身，不再甩锅给 `Beta Browser`。

## 最新结论
- 这次实验目录 `E:\code\_tmp\openvscode-clean` 用的不是 Windows 版 `OpenVSCode Server`，而是官方 release 里仅提供的 `linux-x64` 包。
- 所以在 Windows 机器上，这套实验的 `OpenVSCode Server` 运行链路本来就依赖 `WSL`，不是因为机器被“装成 Linux”了。
- 真正坏掉的点不是 `Wave Beta Browser` 本身，也不是 `Codex` 扩展没装上，而是 `127.0.0.1:9890` 这条 `OpenVSCode Server` 服务没有稳定存活。
- 修复后，`http://127.0.0.1:9890/` 已经恢复返回 `200`，现有 `Wave` 里的两个 `OpenVSCode` webview 也已经重新连上。

  - `Decide how much autonomy you want to grant`

## 新发现的真实卡点
- `Codex` 不再卡在登录页，也不是 `9890` 又死了。
- 真正卡住的是首次引导页 `Continue` 之后的前端收尾：
  - 按钮对应的 React `onClick` 已经存在
  - 但在这套 `Wave -> Beta Browser -> OpenVSCode webview` 链路里，点击后没有继续触发最终的 `onAccept`
  - 结果就是页面肉眼看起来像“按钮失效”
- 这不是后端请求超时：

  - 更像是这个 NUX 页自己的退出/过场流程卡住

## 官方结论补充（2026-03-28）
- 按 OpenAI 官方 `Codex IDE Settings` 当前写法：
  - 扩展确实是围绕 `Codex CLI` 工作
  - 但 `chatgpt.cliExecutable` 明确标成 `DEVELOPMENT ONLY`
  - 官方明确说普通使用“不需要设置它”，手动设置后“部分功能可能异常”
  - `chatgpt.runCodexInWindowsSubsystemForLinux` 的说明里还直接写着：`Codex agent mode on Windows currently requires WSL`
- 所以如果问题是“Codex IDE 扩展在 Windows 上的 agent mode 官方是不是必须走 WSL”，当前官方答案偏向“是”。
- 但这不等于“Codex 在 Windows 所有场景都必须 WSL”：
  - OpenAI 官方 `Windows` 页同时又写了，`Codex` 也可以原生跑在 Windows 上，并使用实验性的 Windows sandbox
  - 所以更准确的说法是：整体 `Codex` 并非一律必须 WSL，但当前 `IDE 扩展 / Windows agent mode` 这条线，官方文档仍偏向 WSL 路线
- 对当前本地实验来说，不只是“文档推荐 WSL”，而是实际运行链路本来就在 WSL 里：
  - `settings.json` 虽然写了 Windows `codex.exe`
  - 但扩展日志仍显示 `Spawning codex app-server`
  - 配合 WSL 侧进程检查，当前这套 `openvscode-clean` 实验实际跑的是 Linux 侧 `codex app-server`

  1. 执行 `npm run dev:linked:stop`
  2. 脚本返回 `running=false`
  3. 但实际上以下东西还活着：
     - `cmd.exe`（launcher）
     - `node.exe ... electron-vite.js dev`
     - `electron.exe` 主进程和子进程
     - `5300` 端口仍在监听
     - `.tmp/dev-linked/current/launcher-state.json` 仍存在
- 这说明旧脚本存在一个很危险的误导链：
  - `stop` 会**假装停干净**
  - `status` 会**误报当前实例不存在**
  - 下一次 `start` 就可能叠在旧实例上，形成：
    - 旧 renderer / 旧 Electron / 旧 state file / 新启动请求 混在一起
  - 这种混合态，正是“有时白屏、有时加载中、有时状态对不上”的高概率来源
- 这轮已对 `scripts/dev-instance.ps1` 做的根治性调整：
  1. **不再只靠 `taskkill` 碰运气**
     - 改成先按当前 `StateSlot`、`dev.log`、`launcher-state.json`、进程树收集整批 dev 实例相关进程
     - 按叶子到根逐个强制结束
     - `Stop-Process` 失败时再 fallback 到 `taskkill`
  2. **`stop` 必须真停干净**
     - 增加循环校验
     - 只要还有残留 `cmd/node/electron/wavesrv/esbuild`，就继续清理
     - 清不掉就直接报错，不再谎称“已停止”
  3. **`start` 不允许叠旧实例**
     - `Start-DevInstance` 先执行新的强校验版 `Stop-ExistingDevInstance`
     - 旧实例没清干净时，直接失败，不再继续起新实例
  4. **`status` 不再只看单个 pid**
     - 改成返回：
       - `matching_process_count`
       - `matching_process_preview`
       - `stale_state_file`
     - 也就是以后能直接看出：
       - 有没有残留实例
       - state file 是真的还是假的
       - 当前识别到的是哪一批进程
  5. **修掉脚本内部两个实际 bug**
     - `Get-DescendantProcessInfo` 的返回类型错误
     - `foreach ($pid ...)` 误撞 PowerShell 只读内建变量 `$PID`
