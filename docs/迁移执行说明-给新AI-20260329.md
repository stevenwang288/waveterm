## 6. 开发版怎么启动，才不会顶掉正式版

### 6.1 必须使用的入口

不要拿裸的 `npm run dev` 充当默认开发入口。优先使用：

1. 启动：
   - `npm run dev:linked`
2. 查看状态：
   - `npm run dev:linked:status`
3. 停止：
   - `npm run dev:linked:stop`
4. 需要验证首启 / 冷状态 / 初始化迁移时：
   - `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/dev-instance.ps1 -Action start -FreshState`

### 6.2 为什么它不会顶掉正式版

`scripts/dev-instance.ps1` 不是普通启动脚本，它显式把开发版状态隔离到了：

1. `.tmp/dev-linked/current/config`
2. `.tmp/dev-linked/current/data`
3. `.tmp/dev-linked/current/electron-userdata`

并且启动前写入：

1. `WAVETERM_CONFIG_HOME`
2. `WAVETERM_DATA_HOME`
3. `WAVETERM_ELECTRON_USER_DATA_HOME`

结论：

1. 正确走 `dev:linked` 链时，开发版和正式安装版不共享用户数据
2. 真正危险的是：
   - 不走隔离脚本
   - 乱开多个实例
   - 旧实例不关又继续拉新实例

### 6.3 一个关键坑

旧问题不是“Electron 容易坏”，而是我们曾经把 `dev:linked` 写成了“默认每次强制 fresh”。

这会导致：

1. 每次都像首启
2. 每次都冷缓存
3. 再叠加首屏依赖重时，就特别容易出现空白壳

当前正确规则：

1. `dev:linked` 默认应保持持久化隔离状态
2. 只有明确验证首启时才用 `-FreshState`

## 7. 开发版怎么测试

### 7.1 前端改动后的最低动作

1. 执行：
   - `npm run build:dev`
2. 重启隔离实例：
   - `npm run dev:linked:stop`
   - `npm run dev:linked`
3. 检查状态：
   - `npm run dev:linked:status`

### 7.2 只要碰了 Go / starter layout / backend 启动链

不能只跑前端构建，必须额外执行：

1. `npm run build:backend:windows`

原因：

- `npm run build:dev` 不会重打 Go 后端 `wavesrv`
- 这就是之前“源码改了，窗口还是老的 Goose/DeerFlow”反复出现的根因

### 7.3 真实验证要看什么

1. `dev.log` 至少要出现：
   - `Init Bare`
   - `Init Wave imported App`
   - `Wave First Render Done`
2. 最终必须看真实窗口
3. 默认布局应回到：
   - `term + sysinfo + web + preview`

不要只看日志就宣布没问题。

## 8. 安装包应该怎么打

### 8.1 标准入口

优先使用：

1. `npm run release:win`

如果明确接受 dirty 工作树打包，再使用：

1. `npm run release:win:allow-dirty`

### 8.2 这条脚本实际会做什么

`scripts/release-win.ps1` 会做：

1. 检查 git 工作树是否干净
2. 执行：
   - `npm run build:prod`
3. 再执行：
   - `npm run package:win`
   - 或 `npm run package:win:allow-dirty`
4. 找到主安装包：
   - `make/<version>/WAVE-win32-x64-<version>.exe`
5. 复制一份到：
   - `D:\DeSK`
6. 输出复制后文件的 `sha256`

### 8.3 复制到 D 盘 desk 的规则

默认桌面目录参数已经写死在脚本里：

1. `DeskDir = "D:\\DeSK"`

复制后的命名规则：

1. `D:\DeSK\WAVE-win32-x64-<version>-fix-<sha>.exe`

所以：

1. 如果要求“打包完自动在 D 盘 desk 放一份”
2. 当前仓库已经原生支持
3. 不需要新 AI 再额外写复制脚本

### 8.4 打包前最容易犯的错

如果你动了：

1. `pkg/**`
2. `cmd/**`
3. `schema/**`
4. starter layout
5. backend 启动逻辑

正确顺序应该是：

1. `npm run build:prod`
2. `npm run build:backend:windows`
3. `npm run release:win`

否则会发生：

1. 前端是新的
2. 包里的 `wavesrv` 还是旧的
3. 最终用户装到的是“源码和安装包不一致”的半新半旧版本

## 9. 为什么之前总容易启动错、启动空白、或者没有内容

这是迁移时必须写给新 AI 的坑点，不然它会重复犯错。

### 9.1 启动错到 Goose / DeerFlow

根因不是一个点，而是两个点一起污染：

1. `frontend/wave.ts`
2. `pkg/wcore/layout.go`

### 9.2 窗口起了但没内容

典型根因：

1. `frontend/wave.ts` 顶层同步依赖太重
2. `modalregistry` 首屏静态导入，提前把 `builder / onboarding / monaco` 拉进来

关键文件：

- `frontend/wave.ts`
- `frontend/app/modals/modalregistry.tsx`
- `frontend/app/modals/modalsrenderer.tsx`

### 9.3 明明改了源码却还是旧界面

根因：

1. 只跑了 `npm run build:dev`
2. 没重打 `wavesrv`

### 9.4 不再报错但一直加载中

根因：

1. fallback atom 能防 crash
2. 但也会把真正的 workspace hydration 问题伪装成“加载中...”

所以迁移时必须同时保留：

1. 首屏日志点
2. 真实窗口验证

## 12. 一句话结论

这次迁移最容易翻车的不是“功能太多”，而是三件事：

1. 把已经放弃的实验线又迁回去
2. 把 `dev:linked` 隔离语义弄丢，导致开发版污染正式版
3. 只重打前端，不重打 Go 后端，最终做出和源码不一致的安装包

只要先按本文处理这三件事，后续重构和删减才不会再次跑偏。
